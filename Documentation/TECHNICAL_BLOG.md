# Building a reproducible restaurant intelligence workflow with Spark

DineIQ was built around a practical problem: restaurant teams often have order, menu, customer and operations records but no shared explanation of what those records mean. A useful system must do more than draw charts. It needs a reproducible data path, explicit quality decisions, traceable analytics and an interface that a non-technical operator can understand.

The project starts with a seeded synthetic generator. The generator creates eleven related entities and injects controlled dirty cases such as duplicates, missing values, invalid quantities and formula deviations. Keeping those cases in the source is important because validation is part of the product evidence. A clean sample without known failures would only show the happy path.

Spark ingests the CSV tables with explicit schemas, writes processed Parquet and computes versioned aggregate tables. The application does not recompute business facts on every request. It loads the verified result tables and checks their paths, row counts and manifest provenance before making them available to the API. This makes the evaluator path fast and reproducible while keeping the historical HDFS workflow available for batch processing.

The analytics layer covers menu contribution and margin, customer recency/frequency/monetary behaviour, basket associations, restaurant and channel comparisons, ratings, inventory, wastage and observed pricing or promotion patterns. The formulas are documented in the DineIQ Guide so a user can ask “profit formula kya hai?” and receive an explanation with a source reference. The assistant is intentionally grounded and deterministic: it will not invent a number when the loaded evidence cannot answer a question.

Demand forecasting is evaluated against a seasonal baseline at restaurant-hour scope. Spark and Python comparison artifacts record the feature semantics and the cases used for agreement checks. That distinction matters because a technical comparison is not the same thing as a business-impact experiment. The same discipline applies to wastage, recommendations and pricing. Wastage is a low-precision screening signal, recommendations are candidates for review, and historical price or promotion effects are descriptive rather than causal.

Data quality is handled as a first-class output. The strict validation run records the complete rule catalog, accepted records, quarantined unique records and removed duplicate copies. Rejected parent records cascade where foreign-key integrity requires it. The accepted and quarantine outputs are separate and readable, so an evaluator can inspect what happened to malformed input instead of relying on a hidden log line.

The serving design separates canonical analytics from operational state. SQLite stores users, roles, audits and management records; it does not overwrite the analytical Parquet or models. The API protects dashboard and operational routes with authenticated sessions and records administrative actions. The supplied Docker path runs Waitress with a read-only bundle mount and a persistent state volume.

Portability was tested explicitly. Docker/Linux loads the saved Spark pipelines. On Windows, Hadoop native helpers may be unavailable, so the serving bundle can use PyArrow to read verified Parquet and bounded local predictors for dashboard inference. The health endpoint labels this mode, preserving the difference between “dashboard is usable” and “persisted Spark model parity is verified.”

The final evidence package combines the source, lock files, serving manifest, test reports, quality catalog and operator guides. It also states what is outside the claim: public hosting, a public full-data URL, managed TLS/secrets, uptime guarantees, causal promotion analysis, operational-grade wastage prediction and broader item/category/location forecast scope. Those boundaries make the submission easier to evaluate because the working product and the remaining external actions are visible in the same package.
