# Assumptions and Limitations

This document records the key assumptions, scope boundaries, and limitations of the DineIQ project and evidence package.

## 1. Synthetic data generation

The restaurant dataset is synthetic and reproducible. It is generated by a fixed-seed pipeline and is not a live production dataset. The generator intentionally includes controlled dirty-data patterns to demonstrate profiling, validation, and cleaning. Because the data is synthetic, conclusions must be treated as evidence-backed examples rather than operational claims about a real business system.

## 2. Canonical data volume and scale

The canonical full dataset contains approximately 650,000 orders and 3,000,600 order-item rows. This is the canonical source used for Spark v4 analytics and HDFS evidence. The 5,000,000-row benchmark is not the same as a canonical 5M production dataset. It is a real scalability workload created by adding 2,000,000 disposable benchmark copies on top of the canonical 3,000,000 order-item base, and the repository preserves the benchmark distinction explicitly.

## 3. Benchmark composition and scope

The 5M benchmark is intentionally documented as:

- 3,000,000 canonical v4 order-item rows
- 2,000,000 disposable benchmark copies
- dataset expansion for runtime validation only
- not a canonical persisted HDFS production dataset

The benchmark remains a PARTIAL fulfillment for any requirement that specifically requires a canonical 5M HDFS dataset validation.

## 4. Descriptive vs predictive churn analysis

The churn-related analytics in the project are descriptive and observational. They identify engagement gaps or inactivity patterns from historical records rather than a validated predictive churn model. This repository does not claim a causal churn forecast or a production-facing predictive churn classifier without separate label preparation and evaluation.

## 5. Observational promotion and pricing analysis

Promotion and pricing insights are derived from historical observational data. They are useful for dashboarding and rule-based discovery, but they do not establish causality. Promotion and price effects remain subject to confounding by seasonality, stockouts, channel mix, menu exposure, and concurrent events.

## 6. Wastage model limitations

The wastage-risk model is a low-precision screening signal. It is suitable for triage and prioritization, not for direct operational decision-making without additional validation. It does not claim causal attribution of waste to specific preparation or replenishment choices.

## 7. Spark/Python weekday encoding differences

The demand comparison between Spark and Python includes a documented feature-semantic difference: Spark uses Sunday=0 while the Python-trained model uses Monday=0. This means that row-wise prediction comparisons are descriptive, not fully feature-equivalent, unless separate retraining with aligned semantics is performed.

## 8. Historical Spark monitoring

The app reports historical job and evidence state only. It does not claim a live Spark monitoring stream or a live production cluster status page. The job-status behavior is intentionally truthful about historical evidence rather than real-time monitoring.

## 9. Local environment assumptions

Batch processing and historical regression require Docker-backed HDFS and Spark. The evaluator serving path uses the exported, checksum-verified bundle in a Linux container with no HDFS connection. Native Windows serving is supported through a PyArrow Parquet reader and bounded local fallback predictors when Hadoop native helpers are unavailable; this is a portability path for dashboard access, not evidence of Spark model parity. Docker/Linux remains the exact persisted Spark model path. See INSTALLATION.md.

## 10. Deployment limitations

Public deployment remains unverified. The repository now supplies portable serving artifacts, Waitress, pinned Python requirements, local evaluator registration and production configuration checks. It does not provision a public URL, managed secret service, TLS certificate, production monitoring, load testing or an uptime guarantee. Image digests and package hashes are not locked. Managed secrets/TLS instructions describe operator work required before shared hosting, not a completed deployment.

## 12. Forecasting scope

Verified demand forecasting is at restaurant-hour scope and includes a seasonal baseline. Full item/category/location forecast scope remains broader than current evidence. The saved models were trained on historical canonical v4, not the new strict validation subset.

## 13. Recommendation scope

Directional basket rules and API recommendations form a candidate recommendation engine. Business impact, acceptance, incremental profit and causal uplift have not been validated. Pricing and promotion outputs are descriptive analyses, not a fully validated decision engine. Wastage test precision is about 9.1%; the risk signal is not operational-grade production prediction.

## 14. Strict validation versus historical analytics

The v2 strict validation evidence covers all 11 input tables: 4,148,987 source rows, 3,741,941 accepted rows, 406,371 quarantined unique records and 675 removed duplicate copies. Rejected parents cascade. The full rule catalog is in DATA_QUALITY_VALIDATION.md. This narrower subset is separate from canonical v4; recomputing downstream analytics and retraining on it remains unperformed. Historical dashboard/model evidence must not be represented as validation of the new subset.

## 11. Reporting caveat

All analytics and model metrics should be interpreted with the repository’s evidence files and audit matrices as the source of truth. Numerical claims are only as strong as the documented verification conditions, the synthetic dataset assumptions, and the known feature limitations recorded here.
